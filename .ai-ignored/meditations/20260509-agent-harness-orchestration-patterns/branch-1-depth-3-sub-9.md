## Subfocus Rationale

This narrowing addresses the fundamental design tension underlying all inter-agent data exchange in the system: why use a format (markdown + YAML frontmatter) that is neither optimally machine-parseable nor formally schema-validated, when strict JSON or protocol buffers exist? The answer reveals a deliberate three-layer architecture optimized for an unusual consumer profile — LLMs as primary readers.

## Discoveries

### Memory d5e503c — Ordering carries semantic weight in CRUX
The phase-block ordering learning demonstrates that even the *sequence* of compressed symbols matters to LLM consumption. This is a property unique to natural-language-proximate formats. In JSON or protobuf, key ordering is either undefined or irrelevant to parsing. In CRUX notation consumed by an LLM, top-down reading order influences which rule is "most salient." The format is designed around cognitive processing, not parsing.

### Memory 96a7410 — Prose-defined schemas drift silently
The tooling-defaults redflag directly illustrates the cost of the human-readable choice: `crux-utils.py` defaulted to 20% while `CRUX.md` specified 25%. Without formal schema validation (JSONSchema, protobuf IDL), the only way to catch this is grep-driven auditing. A typed config with a single source of truth would make this class of bug impossible.

### The frontmatter parser (`crux_mcp_server/utils/frontmatter.py`)
The actual parsing implementation is 39 lines — split on `---`, `yaml.safe_load`, catch errors, return empty dict on failure. No type coercion guards, no required-field validation, no enum checking. The `parse()` function silently returns empty frontmatter on malformed files. This is intentional resilience (don't crash on corrupt data) but it means invalid memories can exist undetected until a downstream operation fails.

### The memory-index.py script
The index builder has explicit warning paths for: no frontmatter, malformed frontmatter, YAML parse errors, non-mapping frontmatter. It logs warnings but continues processing. This defensive approach trades correctness guarantees for system availability — a typical choice when the format prioritises human editability over machine strictness.

### The `.crux/` directory split: JSON for config, YAML for indexes
- `crux-memories.json`, `crux.json`, `dist-manifest.json`, `crux-release-files.json`, `pending-compression.json` — all JSON
- `memory-index.yml` — YAML
- `reference-tracking/*.refs.yml` — YAML

The boundary is clear: JSON where programs are the primary writer/reader and correctness is critical (config, manifests). YAML where the data is generated by scripts but may need human inspection/debugging (indexes, trackers).

### The three-format stack in memory files
A single `.memory.crux.md` file contains all three format layers simultaneously:
1. **YAML frontmatter** — structured metadata (id, title, type, strength, tags)
2. **Markdown body** — human/LLM readable content (or CRUX-compressed body)
3. **CRUX notation** — token-optimized symbols (`⟦⟧`, `Ρ{}`, `→`) that only an LLM with CRUX.md context can decompress

This means a single file requires three different parsing strategies depending on the consumer: YAML parser for metadata, markdown renderer for display, CRUX decompression for semantic understanding.

## Connections

### The consumer-optimized format pyramid

```
        CRUX notation (LLM-only, token-minimal)
       /                                        \
      / compressed body for constrained context  \
     /____________________________________________\
    |   Markdown body (LLM + human readable)      |
    |   agent definitions, skill files, memory    |
    |   bodies — directly interpretable           |
    |_____________________________________________|
   |  YAML frontmatter (human + machine)          |
   |  structured metadata, key-value pairs        |
   |  ambiguous types but readable in diffs       |
   |______________________________________________|
  | JSON config (machine-primary, human-readable)  |
  | strict parsing, no type ambiguity              |
  |________________________________________________|
```

Each layer serves a different consumer at a different priority:
- JSON → CI/CD tooling, install scripts (must parse without ambiguity)
- YAML frontmatter → Git diffs, human review, indexing scripts (must be scannable)
- Markdown → LLMs processing agent/skill/memory definitions (must be interpretable without deserialization code)
- CRUX → Token-constrained LLM context windows (must preserve semantics in minimal tokens)

### The "no formal schema" choice is deliberate, not accidental

The Validate operation in the memory CRUD skill is prose-defined:
> "Check all required frontmatter fields are present: id, title, description, type, strength, created, modified, source, tags"

This is *not* JSONSchema. It's an instruction to an LLM agent performing the validation. The validator is the LLM itself, not a static analysis tool. This means:
- No IDE autocomplete for frontmatter fields
- No compile-time guarantees
- No pre-commit validation hooks (beyond what a Python script can grep for)

But it also means the schema can evolve additively without tooling updates. Adding `consolidated_from` or `consolidation_topic` required updating only the prose documentation and the LLM understood the new fields immediately. No schema migration, no generated code, no version negotiation.

### CRUX notation as a fourth format — neither human nor machine standard

CRUX is purpose-built for a specific consumer that didn't exist when traditional serialization formats were designed: a token-counting LLM that reads sequentially and benefits from semantic density. It has properties of neither:
- Not human-readable (symbols like `Ρ{}`, `Κ{}`, `Φ.*{}` require the CRUX.md key)
- Not machine-parseable by conventional tools (no parser exists; the "parser" is an LLM with context)
- Not standardized (custom per-project, version-locked to CRUX.md)

Yet it achieves 5-10x compression while preserving all actionable information — a trade-off impossible in any format designed for traditional consumers.

### The git-trackability imperative

All four format layers share one constraint: they must be plain text that git can diff, merge, and track. This eliminates:
- Binary formats (protobuf, MessagePack, SQLite)
- Database-backed stores (requires server, not portable)
- Deeply nested JSON (technically text, but diffs are noisy and merges conflict-prone)

The system trades parsing strictness for collaboration tooling compatibility. Every inter-agent artifact can be `git diff`'d, `git blame`'d, and reviewed in a PR. This is not a theoretical benefit — memory 6c16dc6 documents that adversarial verification catches real documentation gaps at a 25% hit rate. That verification runs on diffable text.

### The cost is real but bounded

1. **YAML type coercion** — `"true"` vs `true`, `1.0` vs `"1.0"` — the config uses quoted strings for feature flags (`"true"` not `true`) to avoid this
2. **No formal validation tooling** — the Python scripts do defensive parsing with fallbacks, not strict rejection
3. **Schema drift** — memory 96a7410 directly documents this risk manifesting
4. **Three parsers needed** — the MCP server has separate modules for frontmatter parsing, text search extraction, and YAML index loading
5. **CRUX decompression cost** — requires loading CRUX.md into context (828 lines) before any compressed content is interpretable

But the benefits compound:
- Zero deserialization code needed for LLM consumption
- Instant human auditability without tooling
- Git-native versioning and collaboration
- Additive schema evolution without breaking changes
- A compression path (CRUX) available when token budgets tighten

## Summary

The system's format choices reflect a deliberate optimization hierarchy: **LLM comprehension > human reviewability > git trackability > machine parsing strictness**. JSON handles the narrow case where machine parsing must be unambiguous (config). YAML frontmatter handles the case where structured metadata must be both machine-indexable and human-diffable. Markdown bodies handle the primary consumer — LLMs interpreting agent/skill/memory definitions without deserialization. CRUX notation handles the edge case where even markdown is too token-expensive. The cost is real (no formal schemas, type coercion risks, drift between prose specs and implementations) but bounded by the fact that the primary "parser" — the LLM — is robust to these ambiguities in ways traditional parsers are not. The format stack is optimized for a world where the most important code reader is not a compiler but a language model.
