# crux-judge

Independently assess the repository or a specific engineering plan for quality, feasibility, and completeness.

**Repository**: [github.com/zotoio/CRUX-Compress](https://github.com/zotoio/CRUX-Compress)

## Usage

```
/crux-judge                                          - Assess the entire repository
/crux-judge plans/20260403-memory-system              - Assess a specific plan by directory
/crux-judge plans/20260403-memory-system/plan-memory-system-20260403.md  - Assess by index file path
```

## Instructions

When this command is invoked, spawn a **fresh `crux-planner` subagent** to perform an independent assessment. The planner uses the `crux-judge-plan` skill for the assessment workflow. Using a fresh agent avoids bias from prior sessions.

### Argument Handling

- **No arguments**: Assess the entire repository — audit codebase health, structure, test coverage, documentation, CRUX sync, and convention compliance. Write the report to `plans/assessment-repo-[yyyymmdd].md`
- **Directory path**: Assess the plan in the specified directory (finds the `plan-*.md` index file automatically). Write the report to that plan's directory
- **File path**: Assess the plan using the specified index file directly. Write the report to that plan's directory

Pass `$ARGUMENTS` to the subagent as the target to assess.

### Mode 1: Repository Assessment (no arguments)

When invoked without arguments, the judge performs a comprehensive repository-level audit:

1. Explores the full codebase structure (agents, skills, commands, hooks, tests, scripts, config)
2. Evaluates six dimensions adapted for repo health:
   - **Completeness**: Are all agents, skills, commands properly wired? Are there orphaned or missing files?
   - **Feasibility**: Is the current architecture sustainable? Are there scaling concerns?
   - **Structure**: Are directory conventions consistent? Are dependencies between components clear?
   - **Specificity**: Are agent/skill/command definitions concrete with clear responsibilities?
   - **Risk Awareness**: Are there security concerns, untested code paths, missing error handling?
   - **Convention Compliance**: Do all files follow established patterns (frontmatter, naming, testing)?
3. Runs `integrity-expert` checks (shell scripts, CRUX sync, CI/CD, config consistency)
4. Produces a report at `plans/assessment-repo-[yyyymmdd].md`

### Mode 2: Plan Assessment (with path argument)

When invoked with a plan path, the judge assesses that specific plan:

1. Loads the plan index and all subtask files
2. Explores the codebase to verify assumptions in the plan
3. Evaluates six dimensions: Completeness, Feasibility, Structure, Specificity, Risk Awareness, Convention Compliance
4. Audits the dependency graph for correctness
5. Checks each subtask for quality (clear objectives, concrete deliverables, correct agent assignments)
6. Performs risk analysis
7. Produces a report in the plan's own directory as `assessment-[feature-name]-[yyyymmdd].md`

### Verdicts

| Verdict | Score | Action |
|---------|-------|--------|
| **Approve** | 4.0+ | Repo is healthy / plan is ready for `/crux-execute` |
| **Conditional** | 3.0–3.9 | Address the listed findings before proceeding |
| **Reject** | < 3.0 | Significant issues — needs rework |

### Assessment Report Locations

**Repo assessment** (no arguments):

```
plans/
└── assessment-repo-20260403.md                       ← generated by /crux-judge
```

**Plan assessment** (with plan path):

```
plans/20260403-memory-system/
├── plan-memory-system-20260403.md
├── assessment-memory-system-20260403.md               ← generated by /crux-judge
├── subtask-01-memory-system-foundation-20260403.md
└── ...
```
